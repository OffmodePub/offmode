# migration — Flyway H2/MySQL 이중 마이그레이션 생성

offmode는 dev/prod 모두 `ddl-auto: validate` 라, 엔티티를 바꿔도 스키마가 자동 반영되지 않는다.
**반드시 H2와 MySQL 양쪽에 같은 버전의 마이그레이션을 동시에 추가**해야 한다. 이 스킬이 그 누락을 막는다.

대상 디렉토리:
- `backend/src/main/resources/db/migration/h2/`
- `backend/src/main/resources/db/migration/mysql/`

## 1. 다음 버전 번호 계산

양쪽 디렉토리의 최신 `V{n}__*.sql` 을 스캔해 **둘 중 더 큰 n + 1** 을 다음 버전으로 정한다 (두 디렉토리는 항상 같은 버전 집합을 유지해야 함 — 어긋나 있으면 사용자에게 먼저 알린다).

```bash
ls backend/src/main/resources/db/migration/h2/    | grep -Eo '^V[0-9]+' | sort -V | tail -1
ls backend/src/main/resources/db/migration/mysql/ | grep -Eo '^V[0-9]+' | sort -V | tail -1
```

## 2. 변경 내용 파악

사용자가 설명한 스키마 변경(테이블 추가/컬럼 추가/제약 등)과, 관련 JPA 엔티티(`boundedcontext/<domain>/entity/*.java`)를 Read 해서 컬럼명·타입·nullable·기본값·인덱스를 엔티티와 정확히 일치시킨다. enum 필드는 AttributeConverter로 String 저장되므로 `VARCHAR`로 매핑.

## 3. 두 파일 동시 생성

파일명: `V{n}__{snake_case_description}.sql` (양쪽 동일 파일명).

기존 V5 등 최근 마이그레이션을 템플릿으로 읽어 **방언 차이를 반영**한다:
- **H2**: 보통 표준 SQL. `AUTO_INCREMENT` 또는 `GENERATED BY DEFAULT AS IDENTITY`, 타입은 기존 H2 파일 관습 따름.
- **MySQL**: `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`, `AUTO_INCREMENT`, `DATETIME` 등 기존 MySQL 파일 관습 따름. (문자열 컬럼 collation 이슈는 과거 V3에서 다뤘으니 참고.)

두 파일의 **논리적 스키마는 동일**해야 하고 방언 문법만 다르다.

## 4. 검증

```bash
cd backend && ./gradlew test
```
`FlywayMigrationTest` 가 마이그레이션 적용을 검증한다. 통과 확인 후, 생성한 두 파일 경로와 핵심 DDL을 사용자에게 보고한다.

## 주의

- **한쪽만 만들지 않는다.** H2/MySQL 둘 다 없으면 실패로 간주.
- 이미 적용·커밋된 마이그레이션 파일은 절대 수정하지 않는다(Flyway 체크섬 깨짐). 변경은 항상 새 버전으로.
- 시드 데이터가 필요하면 별도 `V{n}__seed_*.sql`로 분리 권장(기존 `V2__seed_missions.sql` 패턴).
- `git commit/push` 자동 실행 금지. 커밋 메시지(`[Feat]/[Chore] #N ...`)는 제안만.
